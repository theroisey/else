# Selected-provider connection and credential catalog

[#119](https://github.com/theroisey/else/issues/119) expands the existing private catalog for the user-selected GA4 and WooCommerce providers under #26/#27. Apply migration 22 before the new API. The existing [frontend compatibility](provider-workspace-compatibility.md) is independently reviewed in #117/PR #118. No setup endpoint, credential ingestion, external traffic, synchronization, metrics, account seed or verified provider success is enabled by this catalog.

| Provider | Private immutable account identity | Credential encryption purpose |
| --- | --- | --- |
| `meta_ads` | Canonical positive decimal ad account ID, 1–32 digits | `access_token`, unchanged |
| `ga4` | Canonical positive decimal property ID, 1–20 digits; no `properties/` prefix | `provider_credential` |
| `woocommerce` | Canonical HTTPS store base described below | `provider_credential` |

WooCommerce identities contain a lowercase ASCII dotted DNS host, at most 253 characters with 1–63-character labels, alphanumeric label ends and an alphabetic TLD start. Optional path segments contain only ASCII letters, digits, `_` or `-`, with a total path limit of 256 characters and whole identity limit of 520 bytes. Omit the root/trailing slash. Userinfo, ports, query, fragment, percent/dot escapes, direct IP literals and undotted hosts are refused. These are deliberately narrow **syntax rules**, not network destination or ownership verification. Subdirectory stores are supported; other URL forms remain unavailable rather than silently normalized.

Future transport must independently verify provider ownership/authorization and protect DNS, public destinations, TLS, redirects, fixed endpoints, credentials, deadlines, response sizes and background execution. An internal-looking dotted name can satisfy syntax: the catalog makes no request and cannot authorize egress. The generic opaque credential purpose specifies neither OAuth nor a service-account/key-pair format. Future acceptance must verify the actual credential shape and provider policy before storing real secrets.

`catalog.CredentialPurpose` derives the binding from the trusted stored provider. AES-GCM authenticates client, connection, provider and purpose. Meta's exact previous binding/envelopes remain readable; sharing the generic purpose between GA4/WooCommerce does not allow cross-provider ciphertext substitution. SQL enforces the exact provider-purpose pairing even for owner DML. Connection/client/provider/account/creation identity and credential purpose remain immutable. Raw payloads remain bounded to 16 KiB, with the existing retained key and durable reservation rules.

Migration 22 replaces the seven provider-filtered reserve/binding/read/write/local-disable/rotation/inventory functions and the credential guard with their reviewed catalog variants. Existing signatures, owners, revoked PUBLIC, fixed search paths/timezones, runtime EXECUTE grants, fresh authorization/lifecycle locks, revisions/generations and audited transaction boundaries remain. The new syntax helper is private; no new runtime privilege is granted. Public metadata still has exactly seven fields; account identities, generation and ciphertext stay private. Local disable is still a local fence with unavailable remote revocation and manual action, for every provider.

The migration takes the exclusive lifecycle lock and table locks; drain writers and use the separate reviewed migrator before API rollout. Test the immutable artifact/schema/secret/grant pair in isolation. With provider rows present, the frontend must include #117; older Meta-only parsers cannot render those DTOs. No deployment is authorized by this review.
