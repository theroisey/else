## Implemented credential foundation

`backend/internal/integrations/credentials` uses standard-library AES-256-GCM with `cipher.NewGCMWithRandomNonce`. `New` accepts one active key label and up to eight independently provisioned 32-byte keys. Labels and key material must be distinct; unknown active keys, all-zero material and invalid lengths fail. The immutable ring supports concurrent callers and does not retain their key buffers. Encryption uses only the active key; decryption permits explicitly retained keys.

`Seal` accepts 1–16,384 plaintext bytes plus a binding of canonical lowercase nonzero client/connection UUIDs and safe provider/purpose identifiers. Labels/identifiers contain 1–64 lowercase ASCII letters, digits, underscores or hyphens, beginning with a letter or digit. Bindings must come from trusted immutable connection metadata after authorization. Provider and purpose are adapter-owned identifiers, never arbitrary URLs, account labels or credentials. Reassigning a connection to another client/provider is forbidden; a different binding requires an explicitly authorized new connection.

The version 1 binary envelope contains:

| Bytes | Meaning |
| --- | --- |
| First byte | Version `1` |
| Second byte | Key-label byte length `1`–`64` |
| Following label bytes | Key identifier, not key material |
| Next 12 bytes | Cryptographically random GCM nonce generated internally |
| Remaining bytes | Ciphertext and 16-byte authentication tag |

GCM authenticates the exact header and the domain prefix `roisey-else/integration-credential` followed by a zero byte, then the header, then each binding field preceded by a zero byte in client/connection/provider/purpose order. Strict ASCII fields make this encoding unambiguous. The maximum envelope is 16,478 bytes. Changing version, key label, nonce, ciphertext, tag or any binding field prevents successful decryption.

`ParseEnvelope` bounds and copies storage bytes; it does **not** authenticate them. `Open` authenticates before returning a new plaintext buffer. Malformed envelopes, missing/wrong keys, tampering and wrong bindings all return the same fixed `ErrOpen`, with no plaintext. `Rewrap` authenticates the existing envelope, encrypts with the active key and a fresh nonce, then clears its temporary plaintext. It performs no persistence, checkpoint or audit write.

`Envelope.Binary()` explicitly returns a copy for storage. Ring/envelope formatting and structured logging redact values; JSON serialization fails with safe fixed errors. Sensitive fields sit behind private pointers because unsupported formatting verbs can bypass an outer formatter. These safeguards do not protect deliberately extracted byte buffers, reflection/debuggers, memory dumps or plaintext logged by a caller. Never pass keys, plaintext, binary envelopes or provider responses to logs/audits/API responses.

## Key provisioning, parsing and rotation

`ReadKeyring(io.Reader)` accepts a caller-owned protected secret source, limited to 8,192 bytes. It rejects unknown/case-aliased/duplicate fields, duplicate key labels/material, trailing JSON, invalid key sizes and noncanonical padded standard base64. Parser and reader errors discard raw details. The document has this shape; placeholders are intentionally not valid credentials:

```json
{
  "active_key_id": "production-v2",
  "keys": [
    { "id": "production-v1", "key_base64": "<base64 of 32 independently random bytes>" },
    { "id": "production-v2", "key_base64": "<base64 of 32 new independently random bytes>" }
  ]
}
```

Keys belong in a deployment secret manager or protected read-only mounted file, separately from ciphertext/database backups and unique per environment. Never put them in Git, browser bundles, database columns, command-line arguments or log output. Issue #82 wires optional protected Linux loading and database preflight before API listening through INTEGRATION_KEYRING_FILE and INTEGRATION_KEYRING_MODE. Absent configuration disables key-dependent runtime; explicit invalid configuration fails privately. See [startup policy and operating procedure](integration-key-startup.md). No credential producer is enabled by configuring a file.

The raw in-memory primitive has no global counter. The reviewed application encryption path must use the durable budget wrapper below, including rewraps, and rotate before its conservative cap. Direct primitive Seal/Rewrap is for crypto internals and clearly synthetic tests, never a shortcut for credential persistence. Randomness failure is fatal in the standard library; no fixed nonce or plaintext fallback exists.

Rotation requires the later storage owner to provision a new key, retain old keys for reads, switch the active label, authenticate/re-encrypt rows in bounded batches and atomically replace ciphertext using row revision/generation checks. Count each re-encryption toward the new key's budget. Resume from verified checkpoints; do not retire an old key until all live records and every retained backup needing it have expired or been re-encrypted/restored and verified. Restore tests must include both old and new envelopes. Key loss makes affected ciphertext unrecoverable. Re-encryption does not undo compromise of old keys/backups; credential compromise requires provider revocation/reconnection and incident handling.

Callers should clear their input keys and returned plaintext promptly. The reader clears raw document/decoded key buffers, and rewrap clears its plaintext. Go's JSON strings, cipher key schedules and runtime copies cannot be guaranteed erased; this is encryption at rest, not process-memory isolation. Tests use conspicuously synthetic fixed material, never production credentials.

## Durable encryption budgets

`backend/internal/integrations/budget` wraps Seal/Rewrap with a maximum of **2^24 (16,777,216) committed reservations per independently provisioned key**, well below the random-nonce GCM limit of 2^32 messages. Migration 16 stores private immutable labels, SHA-256 fingerprints of independently random key material and monotonic counts. `Keyring.ActiveKeyIdentity` is an explicit backend persistence boundary; labels/fingerprints are never API/log/audit data. Reusing a label with different material or relabeling the same material fails. New material requires a new label; retired accounting remains retained permanently.

For each valid request, the wrapper first commits one counter increment and its mandatory typed `integration_encryption.created` event through the existing audited transaction. A random logical reservation UUID identifies the audit resource; its actor/client, false-to-true exists markers and CLI source disclose no key, label, fingerprint, count, account identifier, plaintext or envelope. The event describes capacity reservation, not encryption/provider/storage success. Failed reservations/audits/commits return no result and perform no encryption. Committed capacity is never refunded, even on cancellation, failed authentication/crypto, uncertain outcomes or later storage failure. There is no automatic retry.

Both guarded functions require current `clients.view` plus `integrations.manage` for the real client and permanently owned connection. View/analytics alone grant no management. Only pending, connected and reauthorization_required connections on active clients can encrypt. Binding comes from trusted metadata with fixed `meta_ads` provider and `access_token` purpose. The reservation takes the shared lifecycle lock before fresh checks; after commit a separate read transaction rechecks access/state and holds that lock through crypto. Revocation/disconnect in the gap burns capacity and returns no ciphertext. The private vault writer below uses the exclusive lifecycle lock and compares the backend result's revision/generation before storing. The wrapper changes no connection state and stores no credential/envelope.

All replicas/reconstructed services must use **one authoritative primary database**. Unique material identity plus row locking serialize allocation without overshooting; runtime receives only the two guarded EXECUTE grants, no table/helper access, and PUBLIC execution is revoked. Guards deny identity changes, skipped/decreasing counters, deletion and truncation. Empty down/up preserves existing metadata/audits and requires regranting recreated functions; any accounting row or matching reservation audit refuses down. Permission catalog/seeds remain unchanged.

The database cap cannot span independent databases or detect a restored/rewound snapshot. Use independent keys in every environment/database. **After every restore/clone/recovery that can rewind counters, provision fresh independent material with a never-used label before encryption. Retained keys are decryption-only. Never resume old-key encryption from backup counts.** Issue #82 adds an explicit declared-restore startup gate; undeclared restore and external material freshness remain operator responsibilities. Stop all writers and follow the [restore procedure](integration-key-startup.md#known-restore-procedure-and-limits). The vault supplies single-row checkpoints and atomic ciphertext replacement. Bulk rotation, key retirement/backup retention and broader recovery tooling remain later work. Losing keys still makes ciphertext unrecoverable.

## Private encrypted credential persistence

Issue #76 adds migration 17 and `internal/integrations/vault`. One private row per connection stores fixed `access_token` purpose, a budget-key identity FK, a framed envelope bounded to 16,478 bytes, positive credential revision/generation and UTC timestamps. Immutable connection/client/provider/account ownership remains in migration 15. No seed rows, HTTP credential route, plaintext read operation or provider call is introduced. Issue #82 supplies optional startup checks separately; verified adapter policy and operational restore safety must precede real credential acceptance.

The backend service provides `Inspect`, `Replace` and `Rewrap`. All require a correlation context, trusted user actor, canonical client/connection UUIDs and fresh independent `clients.view` plus `integrations.manage` on the real active client. Only pending, connected and reauthorization_required connections are eligible. View/analytics permissions confer no credential access. Inspect returns only a private checkpoint `{ConnectionRevision, Generation, CredentialRevision}`; 0 credential revision means absent. It neither reserves encryption capacity nor emits an audit event. Its private read transaction takes the shared lifecycle lock before authorization. Opaque envelopes stay inside the service; no public metadata projection expands.

Replace accepts an exact checkpoint and a caller-owned 1–16,384-byte plaintext buffer. After preflight it seals through the budget wrapper; a separate audited persistence transaction takes the exclusive lifecycle lock, rechecks authorization/state/ownership and compares the budget result's connection revision/generation plus the original credential revision. A successful write advances both revisions and token generation. It changes no connection state; storing a token is not evidence of provider success. Stale/disconnected work, revoked access, archived clients, overflows and audit/commit failures return no success checkpoint or envelope. Already committed reservations remain consumed. There is no automatic retry after an uncertain outcome: reconcile the current checkpoint before deciding a new authorized operation.

Rewrap handles exactly one stored row. Retained-key authentication and active-key encryption use the budget wrapper; the same full CAS prevents overwriting a concurrently replaced token. Both revisions advance, but generation stays unchanged because the token is unchanged. A row from an obsolete connection generation cannot be rewrapped/reactivated; a fresh authorized replacement can supersede it. A restarted service can Inspect and continue from the persisted checkpoint. Every rewrap, including the currently active key, uses a fresh nonce and consumes capacity. Bulk selection/checkpoints, key retirement and restore tooling remain separate work.

`integration_credential.created/updated` and `integration_connection.updated` use only UUIDs, actor/client, exists/revision markers and CLI source, in the same transaction as storage/metadata. The preceding `integration_encryption.created` event means reservation only. No token, key label/fingerprint, generation, account ID, envelope or raw error appears in audits/logs/API responses. Existing generic action/marker readers remain compatible. Runtime receives only two guarded EXECUTE grants, with fixed pg_catalog search path/UTC; no table/helper privileges or PUBLIC execution. The reviewed Go writer enforces audit coverage under the existing application-writer trust model.

Database guards validate envelope framing/label against a registered budget identity with positive reservations, reject ownership changes, skipped/decreasing revisions, generation decreases and deletion/truncation. Successful replacement atomically overwrites the current live envelope; prior envelopes are not archived in that table. Connection metadata, budget identities and audit history remain retained. Backups can still contain prior ciphertext: retain old decryption keys until live-row and backup retention/restore proof permits retirement. This slice supplies no deletion, revocation, purge or key-retirement operation. Empty down/up preserves metadata/accounting and requires regranting recreated functions; any credential row or credential audit history refuses rollback.

The one-primary-database budget rule still applies. Restore/clone/recovery capable of rewinding counts **requires fresh independent active material with a never-used label before sealing**; retained keys become decryption-only. This library cannot detect rewind and adds no operator gate. Parent #24 remains incomplete pending those operational controls and verified provider lifecycle work.

## Confirmed local disconnect

Issue #78 adds `POST /api/v1/clients/:id/integrations/:connection_id/disconnect` with a strict body `{"revision":"<current positive int64 decimal>","confirmed":true}`. The JSON body is limited to 1,024 bytes; duplicate, case-aliased, unknown or missing fields, numbers instead of revision strings, false/null confirmation, trailing documents and query parameters are rejected. Cookie authentication plus the existing exact Origin, JSON Content-Type and session-bound CSRF contract protects this operation. All responses use `Cache-Control: no-store`.

Fresh independent `clients.view`, `integrations.view` and `integrations.manage` are required on the real active client. View is independently required because this public operation returns metadata and supports authorized GET-based recovery; manage does not imply view. Migration 18 supplies one guarded EXECUTE entrypoint, with the exclusive lifecycle lock before fresh authorization, permanent ownership lookup and revision CAS. Runtime gets no table privileges and PUBLIC execution is denied.

An eligible pending, connected, reauthorization_required or disconnect_pending connection changes to `revocation_failed`, with revision and generation incremented together. Existing budget/vault operations immediately deny its use; encryption completed before the disconnect cannot cross the fresh persistence guard afterward. Ciphertext, account ownership, budget identities and history remain retained. No token is read/decrypted, remote request sent or revocation job queued by this operation.

No provider revoker is configured yet. HTTP 200 confirms the **local fence only**, with the seven-field safe connection `data` and `revocation: {"status":"unavailable","manual_action_required":true}`. Stored `revocation_failed` and the explicit response report that remote access has not been revoked. Follow separately verified provider recovery instructions; this is not remote-disconnect success. A disconnected row conflicts, rather than being reinterpreted. Archived clients are denied. Revision/generation overflow returns conflict without changing anything.

A confirmed call with the current revision of an already revocation_failed row returns the same outcome without another mutation, audit or generation increment. The original revision conflicts after a lost response: reload the ordinary authorized GET detail to reconcile before deciding a new operation. No automatic mutation retry exists. Audit/commit failure returns no success and rolls back state/revision/generation together. One `integration_connection.updated` event uses only actor/client/resource UUIDs, exists/revision markers and HTTP source. It means a local metadata change, never an `integration.disconnected` remote outcome. The freshly authorized no-op rolls back its read/row lock through a private sentinel, preserving the audited helper's mandatory-event rule for all mutations.

Errors are fixed and safe: 400 invalid input, 401 absent/disabled session, 403 CSRF/origin failure, 415 non-JSON Content-Type, 404 missing/foreign/denied, 409 stale/invalid transition/overflow, 405 wrong method with `Allow: POST`, and 500 internal failure. Existing metadata paths remain GET-only with `Allow: GET` and their original seven-field projection. No frontend action is introduced on this backend branch.

Migration 18's down removes only the entrypoint under the lifecycle lock; it preserves populated metadata/credentials/budgets/audits, and up requires regranting the recreated function. No permission seed/catalog or credential schema changes. Actual provider revocation/retry/reconnection, credential acceptance and synchronization remain future work in parent #24. Issue #82 supplies the separate declared startup checks described above.

## Frontend permission compatibility

The strict administration catalog/role parsers reject unknown keys. Owner-merged #70 adds client-defined `integrations.view` to the frontend scope map before migration 15 introduces it. Identity parsing preserves structurally valid future keys, while capability checks deny unknown keys. This follows the earlier finance permission-consumer ordering.

Existing administration renders only definitions the real backend returns; there is no new destination or connection action. Metadata reads require both current clients.view and integrations.view on the same client. ## Implemented connection metadata reads

Migration 15 stores one connection per Meta Ads ad account, with permanent connection/client/provider/account ownership and globally unique provider/account identity. Account IDs are canonical positive decimal adapter identifiers of 1–32 digits, private to storage; leading zeros are rejected. The adapter must normalize and verify them before any future insert. IDs, ownership and creation time cannot be updated. Positive int64 revisions and generations support later optimistic writes and stale-work fencing; this metadata slice supplies no lifecycle writer. The later confirmed local-disconnect writer is described above. No connection rows are seeded, and there is no HTTP create/update/delete route.

| Request | Contract |
| --- | --- |
| `GET /api/v1/clients/:id/integrations` | `{data: [...], page: {limit, next_cursor}}`; default limit 25, range 1–100; optional canonical versioned client-bound UUID keyset cursor; ascending connection ID order. |
| `GET /api/v1/clients/:id/integrations/:connection_id` | `{data: {...}}`; no query parameters. |

Each connection exposes exactly `id`, `client_id`, `provider`, `state`, `revision`, `created_at`, `updated_at`. Revisions are canonical decimal strings, preserving int64 precision in JavaScript; timestamps are UTC with PostgreSQL microsecond precision. Provider is `meta_ads`. State is a stored fact: `pending`, `connected`, `disconnect_pending`, `revocation_failed`, `disconnected`, or `reauthorization_required`. A read does not verify remote health or infer success from timestamps. Generation, account ID, credentials/ciphertext, OAuth state/code and raw provider errors never enter the projection.

Both guarded readers take shared advisory transaction lock `871092650209` before fresh authorization and real-client lookup. They require independent current `clients.view` and `integrations.view` for that client; knowing a foreign connection ID grants nothing. Queued reads observe committed assignment/permission revocation and disablement. Missing, foreign and unauthorized resources share 404; malformed requests return 400; absent/disabled sessions return 401; authenticated non-GET requests return 405 with `Allow: GET`. Responses use `Cache-Control: no-store`; internal failures have fixed errors/logs without raw database/provider details. Reads write no audit event. Archived clients retain authorized connection history, and a client without connections returns an empty array.

Migration 15 adds client-defined `integrations.view` as catalog key 34. Only Initial Administrator receives its explicit seed. Custom, Finance and Viewer roles are unchanged; administration can delegate it under existing complete-authority rules. Runtime receives EXECUTE on the two guarded functions, no table privileges, and no ownership-helper access; PUBLIC execution is revoked. Apply migration and reviewed runtime grants before API rollout. Metadata survives disconnect; no deletion API exists. Down takes the exclusive lifecycle lock and refuses any connection or nonseed/revoked integration-view permission history. Empty down/up works, and recreated readers require regranting.

Before accepting credentials or making provider requests, #25 must record and verify the actual Meta API version, fixed endpoints, minimum read scopes, account-ownership proof, reporting contract and OAuth/revocation fixtures. Private credential persistence, budgeted single-row rewrap and optional startup checks are implemented; provider acceptance still needs external provisioning/restore safety and broader rotation/retention proof. Future lifecycle writers require fresh manage plus clients.view, immutable ownership, revision/generation fences and typed transactional audit events. Parent #24 remains incomplete.

## Remaining parent work: design only

The following decisions describe required lifecycle work beyond encryption and metadata reads. Parent #24 remains open with all acceptance boxes incomplete until implemented and verified.

| Boundary | Required behavior and evidence |
| --- | --- |
| Provider approval | #25/#26/#27 record concrete provider, minimal scopes, account ownership/verification, fixed endpoint policy and retention before accepting credentials. No generic normalized metrics schema until a provider consumer needs it. |
| Authorization | View reads are implemented above. Future manage operations additionally require the real session/CSRF contract and fresh checks before lookup, decryption and writes. No implicit view from analytics/manage access. |
| Persistence | Metadata, budget accounting and private encrypted credentials are implemented above, including bounded ciphertext and generation fences. #82 adds protected startup and declared-restore checks with documented detection limits. Sync state, rotation batches and key retirement/backup retention proof remain future work. History-preserving rollback must refuse populated data destruction. |
| Metadata API | List/detail are implemented above. Provider-specific management operations and safe enumerated failure projections remain future work. No route claims connection/sync success without verified work. |
| OAuth | Single-use expiring random state and PKCE bound to actor/session/client/provider, fixed exact callback origin, current authorization at completion and verified account ownership. Exchange secrets backend-only; exclude code/state/query strings from ingress and application logs; reject reuse, expiry, actor changes and unexpected callbacks. |
| Outbound access | Fixed provider-owned HTTPS allowlists, verified TLS, no arbitrary caller-supplied URLs. Deny private/link-local/loopback/metadata destinations, unsafe DNS resolution and cross-host redirects. Bound timeouts, response bytes and pagination. Deployment egress enforcement complements adapter validation. |
| Disconnect | Confirmed local fencing/unavailable remote outcome is implemented above. Actual provider revocation/retry/reconnection remains future work. Remote revocation remains pending/failed until provider evidence confirms it. Keep only encrypted material needed for bounded revocation; terminal failure must expose honest manual recovery. Do not report remote success from local deletion. |
| Synchronization | Explicit queued/running/succeeded/failed/action-required outcomes, attempt/deadline/page budgets, idempotent ingestion keys and checkpoint transactions. Retry only transient failures with bounded backoff; auth/permission failure requires action. Stale or disconnected generations cannot publish metrics/checkpoints. No empty/failure response becomes a successful sync. |
| Audit | Typed, allowlisted transactional connection changes and safe sync outcomes through existing infrastructure. No credentials, callback codes/state, account labels, raw provider errors/responses or customer payment data. Safe activity projections require separate permission policy. |

Next slices must supply deterministic provider fixtures, callback/revocation failure tests, storage privileges/migrations, restart/rotation/restore proof, retry/idempotency tests and real authorization/audit behavior. Concrete remote provider access and production deployment remain separately authorized work. The overview continues to display honest unavailable integration states.
