# WooCommerce read-only synchronization

Related existing issue: [#27](https://github.com/theroisey/else/issues/27). The owner selected WooCommerce; the collection and durable-publication policies were recorded in that issue before implementation. No new issue or application image is required. [Order/refund interpretation](woocommerce-reports.md) remains the exact monetary contract.

## Provider and privacy contract

Verified WooCommerce 11.1.2 is immutable commit [`2316335b1bce366178ce865d4e61a4c5e2219352`](https://github.com/woocommerce/woocommerce/tree/2316335b1bce366178ce865d4e61a4c5e2219352). Its REST authentication supports HTTPS Basic consumer keys/secrets and vendor read permission checks. The [API key generator](https://github.com/woocommerce/woocommerce/blob/2316335b1bce366178ce865d4e61a4c5e2219352/plugins/woocommerce/includes/class-wc-ajax.php) and [hash implementation](https://github.com/woocommerce/woocommerce/blob/2316335b1bce366178ce865d4e61a4c5e2219352/plugins/woocommerce/includes/wc-core-functions.php) produce `ck_`/`cs_` followed by 40 lowercase hexadecimal characters. Parsing rejects all-zero, malformed, duplicate, extra or expanded credential fields; the private two-field JSON is at most 1 KiB. A syntax check cannot verify the key's vendor permission. Operators must provision a dedicated **Read** key. Every compiled application request is GET, including when a mistakenly overprivileged key is supplied.

Official WordPress 6.8 [REST field filtering at immutable commit `5744cd1a13f6da9f09db6d7f14ca66c5bf474ebe`](https://github.com/WordPress/wordpress-develop/blob/5744cd1a13f6da9f09db6d7f14ca66c5bf474ebe/src/wp-includes/rest-api.php) corroborates nested `_fields` and parent/child selection. Official WooCommerce v3 CRUD and inherited v2 order serialization corroborate `dates_are_gmt`, `id` ordering, `include`, `dp` and the selected fields. The earlier archived documentation source remains explicitly archived. Plugins or older/incompatible stores that expand private fields or omit required projections make collection unavailable; the collector does not silently accept their full customer objects.

The store's immutable private account ID is its canonical HTTPS origin, optionally including the validated WordPress base path. No HTTP, IP literals, credentials, explicit ports, queries, fragments, traversal, provider links or caller-supplied endpoints are accepted. The shared HTTPS layer revalidates public DNS answers for each request, pins approved addresses, verifies hostname/TLS trust, rejects redirects and bounds the entire actual request/body lifetime. Basic Authorization is a header, never a query parameter. Credentials, private origins, raw response headers/bodies and diagnostics cannot be serialized into reports, logs or audit snapshots. A successful request demonstrates API read access at the selected origin, not legal ownership or independent vendor-scope verification.

## Complete measured collection

Periods are explicit canonical UTC RFC3339 whole seconds, half-open `[start,end)`, positive and at most 31 days. Select exactly one of USD/EUR/GBP/TRY (two places), JPY (zero) or KWD (three). Order-created grand/lifetime-refund/remainder totals and separately refund-created events are different cohorts; never subtract the latter to invent net revenue. All standard order statuses are retained without payment/recognition inference. Money remains canonical exact minor-unit strings and is never converted through floating point or guessed currency.

The adapter requests `dp=6`, `dates_are_gmt=true`, `orderby=id`, `order=asc`, 100 rows/page and at most five 64-KiB pages/500 rows for each order/refund collection. The vendor's exclusive `after` receives `start-minus-one-second`; `before` receives `end`. Every returned creation time is independently checked against the selected interval. Pagination must have exactly one canonical bounded `X-WP-Total` and `X-WP-TotalPages` value, stable expected counts, contiguous complete pages and strictly increasing unique positive IDs. No query-string key, followable Link header or alternate endpoint is exposed.

Order projections contain only ID/status/currency/GMT date/grand total, embedded refund IDs/totals, and line item ID/product ID/variation ID/integer quantity/net/tax. Refund projections contain only ID/parent ID/GMT date/amount. Their exact parent currencies are independently fetched via compiled order `include` batches of at most 50 IDs, without period filtering so older parents are included. Every requested parent must be present exactly once with only ID/currency and the explicitly selected currency. Missing, extra, private or mixed-currency parents fail atomically.

Product rows group observed original order lines by numeric product/variation IDs, preserve unknown/deleted ID `0`, and report exact quantity, distinct order count, line count, net, tax and their sum. There are at most 50 lines/order and 1,000 groups. There are no inferred product names, stock, paid sales, refund-line allocations, visits or conversion metrics. Line components and order grand totals have different component bases (for example, shipping) and are labeled accordingly; no unsupported reconciliation is invented. The earlier strict six-field order normalizer is preserved separately.

The collector is capped at 120 seconds and no automatic provider retry occurs. Every request rechecks a durable authorization/generation/lease fence. Both collection heads are fetched again and compared byte-for-byte/count-for-count before acceptance. A changed head rejects the entire result. Unchanged heads cannot prove unchanged later rows: WordPress supplies no transactional multi-request snapshot guarantee. Reports expose the bounded actual `collected_from`/`collected_through` UTC interval, not an invented single provider snapshot time.

## API and durable storage

All mutations require a current authenticated session, exact configured Origin, JSON, CSRF, active client and current `clients.view` plus `integrations.manage`. The private origin is globally unique and immutable under existing integration catalog rules. Mutation bodies reject aliases, duplicates, extra fields and more than 4 KiB.

| Operation | Contract |
| --- | --- |
| `POST /api/v1/clients/{client}/integrations/woocommerce` | `{origin}`; returns safe pending connection metadata, without provider access or credentials |
| `POST /api/v1/clients/{client}/integrations/{connection}/woocommerce/credentials` | `{revision,start,end,currency,consumer_key,consumer_secret}`; locally validates/encrypts and atomically queues work |
| `POST /api/v1/clients/{client}/integrations/{connection}/woocommerce/sync` | `{revision,start,end,currency}`; queues explicit refresh using the saved credential |
| `GET /api/v1/clients/{client}/commerce?after={uuid}` | Safe WooCommerce connection metadata, at most 25 rows and `next_id` |
| `GET /api/v1/clients/{client}/commerce/{connection}?start=…&end=…&currency=…` | Stored complete report plus safe synchronization/freshness status |
| `GET /api/v1/clients/{client}/integrations/{connection}/woocommerce?start=…&end=…&currency=…` | Same protected report read |

Queued responses are `{job_id,state:"queued",connection_revision}` with string revisions. Setup never calls the store. The independently committed audited encryption reservation remains burned on later failure. Credential replacement, pending connection state, cancellation of old work, queued job and mandatory audit commit together. Missing encryption configuration leaves authorized reads available and refuses setup.

Report/catalog reads independently require current `clients.view` plus `analytics.view`; this does not grant integration metadata/management access. Responses are `no-store`. A report has `orders`, `refunds`, `products`, `collected_from`, `collected_through`, safe status and actual last-success time. Every section binds client/connection/wc/v3/currency/exponent/exact UTC start/end. Strict Go and SQL boundaries reject private/extra/missing/duplicate fields where raw JSON is available, malformed IDs/periods/counts, unsupported currencies, noncanonical exact values and inconsistent arithmetic. SQL jsonb already canonicalizes duplicate names, so raw duplicate rejection happens before typed publication in Go. Empty complete arrays and exact zero sums are distinct from unavailable observations.

Migration 24 extends the existing private analytics job/snapshot tables with a provider discriminator and mutually exclusive typed parameters. GA4 retains its property-date schema and existing entrypoints; WooCommerce uses UTC-second start/end/currency. The snapshot key is `(connection,generation,provider,typed period,currency)` with nulls treated as equal. Repeating a successful period replaces one snapshot/revision; failed refresh preserves a previous valid current-generation snapshot and its original success time. Replaced/disconnected generations cannot expose old data. Current requested periods/currencies never inherit observations from a different selection.

The shared lifecycle/admission locks and private queue enforce one active job per connection and at most **two unexpired running jobs across GA4 and WooCommerce together**, including multiple worker replicas. Claims commit/audit before key use. Bounded key opening/parsing holds a short lifecycle fence; all transactions end before provider requests. Current requesting-user grants, active client, connection revision/generation, credential revision/generation and random 180-second lease are rechecked before each request and final atomic job/snapshot/connection publication. Rotation, disablement, archive, revocation, replacement, cancellation, expired or reclaimed leases prevent stale publication. Already issued requests cannot be retracted. A worker operation is capped at 150 seconds; only abandoned leases can be reclaimed, up to three attempts. Ordinary provider failure requires explicit retry and exposes a safe reason.

## Same-image worker and retention

The existing `/analytics-worker` binary in the **one application image** now alternates which provider it checks first, falling back when that provider has no claimable work. The shared per-process transport admission and database global leases remain bounded. The API does not start worker/provider work. Supervise this binary or schedule `--once` using the same immutable reviewed application image, protected key source and separately provisioned least-privilege runtime PostgreSQL identity. Apply migration 24 and the updated reviewed runtime EXECUTE grants first. No additional application image is built or published.

Stored measured snapshots expire 90 days after their last successful refresh; at most 100 are pruned with mandatory audit in a transaction. Account/credential/encryption-budget/job/audit history remains retained. Staleness is true without a usable report or when the last success is at least 24 hours old. A failed refresh can display the earlier still-retained report alongside its current failure and actual prior success time. Migration 24 down refuses retained commerce work/snapshots; empty down restores the earlier GA4 functions/schema. It never deletes populated commerce history to make rollback pass.

The selected store must have deployed permitted public DNS/TLS/egress and a dedicated Read key before real use. This environment has no live store credential and its policy does not permit arbitrary store access. Synthetic collection and PostgreSQL tests exercise privacy, exactness, setup and lifecycle; they do not prove actual store ownership, deployed provider access, production supervision or real observed commerce values.
