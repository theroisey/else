# CI and image publication

Related Issue: [#6](https://github.com/theroisey/else/issues/6). `.github/workflows/ci.yml` runs on PRs targeting main, pushes to main, and manual dispatch. Every job uses an explicit timeout, official Actions pinned to resolved full commit SHAs, and read-only checkout credentials. PRs receive no registry credentials or package-write permission.

## Required checks

Release backend #92 stamps the production API using the tested checkout revision and one UTC build timestamp, supplied through strict Docker/Compose-CI arguments. Container integration authenticates disposable synthetic sessions against the actual non-root API and verifies exact metadata plus denied/anonymous/read-only behavior. Backend integration separately verifies the compiled stamp and refusal of runtime overrides. Plain builds stay honestly unavailable; metadata does not certify release, registry provenance or deployment.

This change documents those rules without modifying repository administration. Source checks do not substitute for browser/container/database checks. Fork PR runs have read-only permissions and no registry writes; GitHub may require owner approval before running their code.

Issue [#100](https://github.com/theroisey/else/issues/100) adds Dependency security as a read-only, fifteen-minute job on the same PR/main/manual events. Node 24.21.0/npm 11.19.0 install the committed frontend lock and `npm audit --include=dev --audit-level=info` rejects advisories of every severity. Go 1.27.1 with `GOTOOLCHAIN=local` installs official govulncheck **v1.8.0**, verified at upstream tag/commit `709015412431dd2b5b28a53c06c70bc02d49074c`. [Official usage and exit-code guidance](https://github.com/golang/vuln/blob/709015412431dd2b5b28a53c06c70bc02d49074c/cmd/govulncheck/doc.go) explains the source/symbol analysis and its limitations (including reflection/unsafe and conservative interface calls).

[`check-go-vulnerabilities.sh`](../backend/scripts/check-go-vulnerabilities.sh) runs ordinary **text** output with tests on `./...`, then with `-tags integration`, and finally at `-scan module` level. It statically analyzes integration test dependencies without executing database tests. The final inventory rejects module advisories even when vulnerable packages/symbols are not imported/called. JSON/SARIF/VEX formats can exit successfully with findings and are deliberately excluded as implicit success gates. A vulnerability finding, package/tool failure, or inaccessible registry/database fails the job; there is no suppression, continue-on-error, fake/offline database or empty-output success path. Queries contain module/advisory information, not customer records or deployed credentials. Successful scans are point-in-time evidence and do not replace the [threat model](security-review.md).

For local Go checks, install the same pin with `go install golang.org/x/vuln/cmd/govulncheck@v1.8.0`, add `$(go env GOPATH)/bin` to PATH, and run `sh backend/scripts/check-go-vulnerabilities.sh` from the repository. The managed workspace currently denies `vuln.go.dev`; the script's actual local scan fails rather than reporting clean. This workflow does not change/bypass that policy. Repository CI must supply its own real outcome before review; failed scans or advisories remain open with concrete remediation/disposition.

The Compose runner archives the committed HEAD into a private temporary directory, generates its own credentials/TLS, chooses a random loopback port and unique project/volume, and cleans up those resources on success or failure. Failure logs redact generated passwords and database URLs before cleanup. It never reads the developer's `.env` or uses the ordinary project volume. Invoke `sh backend/scripts/test-compose.sh` after committing the source to be tested. The production images are revision-labelled, inspected for non-root runtime users, and saved only after runtime checks succeed. The companion frontend fix makes Vite's dependency/config cache writable by its non-root Node user; its commits are integrated into the backend CI branch so the combined gate can run before review/merge.

The outage check deliberately stops PostgreSQL and requires `/health` to stay successful while `/ready` returns 503. Recovery explicitly starts the existing stopped service, then polls a local read-only `SELECT 1` at most thirty times with one-second intervals between failed probes. Connection and statement timeouts are two seconds each. A start failure or exhausted probe bound fails with a fixed diagnostic; probe output is suppressed. The independent bounded HTTP readiness check follows database recovery. Initial creation and persistence checks retain their ordinary Compose health waits. This preserves the existing data volume and all TLS/role checks. [Issue #86](https://github.com/theroisey/else/issues/86) addresses the observed `up --wait` failure against an intentionally stopped container.

## Publication and aliases

Publication runs only for main push/manual events after all six jobs pass, including browser authentication and dependency security. The dependency job has only `contents: read` and no runtime/registry credentials; a scan failure blocks publication through the explicit `needs` prerequisite. Publish remains the sole job with `packages: write`; it authenticates to GHCR with GitHub's provided token. No personal access token is required. Its initial publication loads the exact production images saved by the container job from a short-lived same-run artifact; it does not rebuild them. CI run logs, the tested revision label, artifact digest, and GHCR content digests provide infrastructure traceability. Deployment and signed release attestations remain separate work.

Images use `ghcr.io/theroisey/else-frontend` and `ghcr.io/theroisey/else-backend`, with `sha-<full-commit>` and `latest` aliases. Stable versions can be promoted by manually dispatching CI on main with `version: vMAJOR.MINOR.PATCH`; prereleases and leading-zero components are rejected. The entire check suite runs again before promotion. A repeat publication retains an existing SHA image after verifying its revision label; a version alias already assigned to another revision is refused. SHA and version aliases are immutable by this workflow's policy. GHCR administrators can still change tags; production consumers should pin content digests.

Publication jobs serialize. A run whose revision is no longer main's current head publishes its immutable revision but leaves `latest` alone. A registry failure can leave one image published before the other; rerun CI on main to finish without overwriting already-published SHA aliases. Existing version aliases for another revision require a new version, not deletion. Package policy must allow the repository's GitHub token to write its own packages; publication failures remain visible and never trigger deployment.

No image publication is performed from development branches, PRs, or tag pushes. The owner merged PRs #39/#40 and the first main publication succeeded; evidence is recorded below.

## Maintaining pins

Action pins were resolved from official repositories' v4/v5/v3 tags on 2026-10-01. Updates must verify the upstream repository and release, record the reviewed SHA, and rerun checks. Node/npm/Go and application dependencies remain pinned by the repository's version/lock contracts. PostgreSQL, Node, Go, nginx, and the Dockerfile frontend use immutable manifest digests. Node/Go digests were observed in successful CI builds; nginx's multi-platform index was resolved from the registry. The combined runtime gate still determines whether those images work together.

Run `actionlint` (including ShellCheck when installed) against the workflow, `sh -n` on the Compose runner, recovery helper and vulnerability script, `bash -n` on publication, `python3 backend/scripts/test-publication.py`, `python3 backend/scripts/test-dependency-gate.py`, and `python3 backend/scripts/test-compose-recovery.py` locally. Dependency simulations prove both configurations include tests/text output and preserve failure exit statuses from findings/fetch errors on all three scans; the publication test guards all six prerequisite jobs. Recovery regression tests replace Compose and sleep with transient test fixtures to exercise immediate/delayed readiness, the last allowed probe, timeout, start failure, and safe diagnostics. Static validation and simulations do not establish a real clean vulnerability result, actual container recovery, a successful GitHub run or registry upload. Issue #6 is closed after both PR gates and the owner-approved main publication provided that evidence.
