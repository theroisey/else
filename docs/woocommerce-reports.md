# Exact WooCommerce order and refund interpretation

[#115](https://github.com/theroisey/else/issues/115) supplies pure `NormalizeOrders`/`NormalizeRefunds` under [#27](https://github.com/theroisey/else/issues/27), using the user-selected WooCommerce provider. No authorization, credential access, transport, persistence, route, provider success state or frontend is supplied. These reports describe observed rows; they do not prove store ownership, freshness, a provider snapshot, recognized revenue or cash settlement.

## Trusted input and page boundaries

`Expectation` requires canonical nonzero client/connection UUIDs, one selected supported currency, per-page 1–100 and canonical UTC RFC3339 second timestamps for a half-open `[start,end)` period of at most 31 days, starting in year 2000 or later. Supported currencies match the application's existing reviewed set: USD/EUR/GBP/TRY exponent 2, JPY exponent 0, KWD exponent 3. Currency is checked on every order and every refund parent; no shop-default inference, mixed sums or exchange conversion. Multi-currency batches are unavailable under this bounded contract until a separately reviewed partitioning policy exists.

Each `Page` carries the actual trusted request number and canonical decimal `X-WP-Total`/`X-WP-TotalPages` strings. A future transport must reject duplicate/ambiguous headers before constructing it. Accept one to five pages, each at most 64 KiB, with at most 500 rows total. Request page numbers start at one and are contiguous; header totals/page count stay exact and stable; every page has precisely the expected number of rows. An empty collection requires one `[]` response with total/pages zero. IDs must be increasing across pages and unique; IDs are canonical positive JSON integers of at most 18 digits, then retained as strings. Do not follow provider navigation URLs to construct the sequence.

The caller must request decimal precision `dp=6`; the response does not echo or prove that request. Monetary strings require exactly six fractional digits. Conversion to the explicitly known minor-unit exponent accepts only zero discarded digits, so JPY/two-/three-place amounts are exact, without rounding or floats. Each amount is at most 18 minor-unit digits; sums use arbitrary-precision integers and the bounded row count. Unsupported/fractional-subminor/negative/overflow amounts refuse the whole report.

Minimal order objects have exactly `id,status,currency,date_created_gmt,total,refunds`; each embedded refund has exactly `id,total`, with at most 50 per order and no repeated/colliding order/refund IDs. Minimal refund-event objects have exactly `id,parent_id,date_created_gmt,amount`. Objects reject duplicate decoded names (including escaped aliases), case/unknown fields, missing values, null/type errors, malformed UTF-8/trailing JSON and nested reason/customer/payment/metadata fields. This intentionally refuses a full default provider response; the later producer must establish a reviewed minimal projection/request-field policy before using it. Shared provider-internal strict object parsing reuses existing Meta/GA4 behavior.

GMT row dates must be real canonical `YYYY-MM-DDTHH:MM:SS` values inside the expected UTC period; normalization adds `Z` without guessing a shop timezone. Caller transport must verify actual filter boundary semantics and select the complete requested cohort, including exact boundary seconds. Seeing valid in-period rows and matching header counts does not prove filters, store ownership or completeness against concurrent edits. Current extension hooks/custom statuses/format changes can make the contract unavailable; do not substitute zero or silently skip rows.

## Keep cohort and event totals separate

`NormalizeOrders` includes every supported standard status: pending, processing, on-hold, completed, cancelled, refunded, failed and trash. It preserves status without treating it as payment/settlement proof. For orders **created in this period**, return original grand total, the absolute sum of embedded **lifetime** negative refunds and their exact nonnegative remainder, per order and in totals. Reject lifetime refund sums exceeding the original total. No recognized revenue, net sales, paid-cohort amount, tax-exclusive revenue, conversion or average order value is derived.

`NormalizeRefunds` uses the **refund's own creation period** and positive `amount`. Every refund requires one unique explicit trusted `Parent{ID,Currency}`; parents may have been created outside the requested period. Duplicate/missing/wrong-currency or unused parent projections fail. The refund schema does not supply currency, so an absent parent cannot be replaced with a store currency or an order-created cohort default. Refund IDs cannot equal their own parent. Multiple events may share a parent, while each event remains unique. The summed positive refund amount describes this refund-created event set; never subtract it from a differently defined order-created total and label the result revenue.

Every failure returns fixed `WooCommerce report unavailable` and a zero report. Success retains only client/connection/version/currency/period, minimal row IDs/status/dates and exact amounts; no secret, shop URL, account label, customer contact/payment data, refund reason or product text. Complete empty reports have explicit empty arrays and exact zero sums. No missing periods/events are fabricated.

It does not settle shop ownership, SSRF/DNS/redirect/TLS, Basic-header redaction, read-only key verification, retry/rate limits, generation fencing, replacement/revocation, scheduled background isolation, idempotent ingestion/reconciliation, durable sync errors, retention/deletion, product metrics, recognized revenue or measured UI. #27 remains open for those contracts and implementation, with real connection observations distinct from deterministic fixtures.

Tests cover complete/max/empty paging, actual source-shaped synthetic projections, exact values beyond IEEE-754 precision, all six currency exponents, distinct parent/event periods, canonical boundaries and fixed atomic failures for malformed/private/mixed/partial/overflow data. Existing GA4/Meta tests retain their strict contracts. Fuzzing checks both normalizers' no-partial-output, binding and exact arithmetic. Run relevant Go race/vet/static build and all six exact-head CI gates before ready; no test here contacts a provider or presents synthetic commerce as a real account.
